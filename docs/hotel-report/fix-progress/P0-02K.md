## Contract proof

Correct contract: **404 for cross-tenant or nonexistent reservation; 409 only for an authorized reservation whose invoice is not finalized**.

Sources:

1. `docs/audit/system/FULL_SYSTEM_ERROR_EXPECTATION_CATALOG.md` defines `NOT_FOUND` as 404 and requires cross-tenant resources to remain hidden/indistinguishable from missing identifiers.
2. Canonical `PropertyInvoiceController.authorizeInvoice()` throws `ResourceNotFoundException` for unauthorized invoice ownership/property access, while true workflow/state conflicts remain distinct.
3. Existing tenant tests already expect 404 for cross-tenant room, room type, housekeeping, invoice-read and payment resources.

## Root cause and disclosure assessment

`InvoiceController.finalizedByReservation()` queried only for a finalized invoice. Any missing result returned 409 for the POST route before reservation ownership/property authorization. This allowed an unauthorized caller to distinguish this path from ordinary 404 tenant-denial behavior and exposed that the supplied reservation was in a non-finalized invoice state.

Production behavior was wrong. The test expectation was current and security-correct. The repository lookup remains by reservation ID, but authorization is applied before invoice-state evaluation and all denied/missing cases return the same empty 404 legacy response. No tenant ID, property ID, email, owner name, or internal exception is returned.

## Minimal change

- Inject `ReservationRepository` into `InvoiceController`.
- Resolve and authorize the reservation before checking finalized-invoice state.
- Permit system administrator, reservation owner, or staff assigned to the reservation property.
- Return 404 when the reservation is missing or inaccessible; preserve 409 for an authorized, non-finalized reservation.
- Extend only the directly related compatibility and tenant matrix tests.
