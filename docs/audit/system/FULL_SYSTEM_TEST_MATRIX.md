## Purpose and Release Boundary

This is an evidence map, not a test-run report. A cell is `VERIFIED` only when the
referenced evidence contains an executed command and a zero-failure/non-skipped result
for that scenario. `PARTIAL` means the scenario is covered only by a focused slice,
intercepted browser API, H2-only fixture, or an explicitly bounded remediation task.
`GAP` means no executable evidence was found. `BLOCKED_EXTERNAL` means the scenario
requires a provider/mail credential or an approved policy and remains fail-closed.
`N/A` is used only where the scenario cannot mutate state (for example, a read-only
report query); the reason is stated in the cell.

FR-045 requires a clean database rebuild, deterministic seed, and final-worktree
backend, frontend, browser, security, tenant, concurrency, export and reconciliation
runs. FR-046 additionally requires role steps, expected UI/HTTP/database/state/audit
effects, retry behavior and safe reset guidance. The following final-gate artifacts are
not present as of this audit: `docs/testing/evidence/007/final/clean-migration.md`,
`backend.md`, `frontend.md`, `playwright/`, and `reconciliation.md`. Therefore no row
below is a final release certification.

## Coverage Legend

| Marker | Meaning |
|---|---|
| `VERIFIED` | Executed evidence with zero failures/errors/skips for the stated scope. |
| `PARTIAL` | Executed, but limited to a focused layer, H2/intercepted fixture, or a known boundary. |
| `GAP` | Required scenario has no executable evidence in the current worktree. |
| `BLOCKED_EXTERNAL` | Credential, provider, mailbox or approved commercial policy is intentionally unavailable. |
| `N/A` | No mutation is possible for the stated scenario; the reason is recorded. |

The five coverage dimensions are deliberately separate:

| Dimension | Minimum assertion |
|---|---|
| Positive | Authorized input reaches the expected UI/API state and intended persisted effect. |
| Negative | Invalid, unauthorized, stale or tampered input returns the stable error contract and no unauthorized effect. |
| Concurrent/replay | Duplicate or simultaneous requests produce one authoritative effect, or one deterministic conflict. |
| Timeout/provider failure | Expiry, unavailable provider, lost response or client timeout leaves a truthful state and defines safe retry. |
| Rollback/recovery | Failure at a persistence boundary leaves the aggregate consistent; recovery is additive and preserves evidence. |

## Safe Recovery Rules

- Never treat an intercepted Playwright response as proof of backend persistence; rerun
  the journey against the real application and deterministic SQL Server fixture for FR-045.
- A timeout or unknown mutation outcome must reuse the same idempotency key and first
  recover the server result. It must not create a second booking, payment, refund,
  subscription effect, invoice or housekeeping task.
- Invalid callback, permission denial, tenant mismatch, policy blocker and provider
  failure must leave financial rows unchanged except for the append-only audit/diagnostic
  event required by the contract.
- Checkout, refund and subscription corrections are forward-only. Preserve immutable
  ledger/invoice/history evidence; use a credit note, reversal or later lifecycle event.
- Migration recovery is additive: stop new writes, fix the preflight/configuration gate,
  retain created schema/evidence, restore only through an approved backup runbook, and
  rerun deterministic validation. Do not edit applied migrations or delete financial rows.
